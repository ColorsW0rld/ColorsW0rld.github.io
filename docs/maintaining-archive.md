# 维护文章归档

## 首次启用自动整理

这部分由有仓库设置权限的维护者完成一次。普通成员只需遵循根目录 README。

1. 将本次新增的 `.github/workflows/archive-articles.yml`、整理程序、依赖锁文件、`incoming/` 和文档合入默认分支 `main`。在其他分支上的配置不会处理 `main` 的上传。
2. 打开仓库 **Settings → Actions → General**，确认允许运行 GitHub Actions，以及本仓库允许使用 checkout 和 setup-node。workflow 已声明 `contents: write`，用于提交整理结果；它使用 GitHub 自动提供的令牌，不需要成员创建个人访问令牌。
3. 查看 **Settings → Rules → Rulesets** 或 **Branches**。机器人需要能推送到 `main`。若组织策略或保护规则禁止直接推送，不要为省事关闭必要的保护；改为符合仓库规则的 PR 归档流程后再向成员开放。当前实现不会绕过这些规则。
4. 打开 **Actions → 整理上传的微信文章 → Run workflow**，选择 `main`，运行一次。收件目录为空时应成功，显示没有待处理 HTML，也不会创建空提交。
5. 用一篇尚未归档的真实文章完成 README 的上传流程，确认自动整理生成了机器人提交、`incoming/` 中该文件已移走、首页新增链接。失败时查看运行摘要。
6. 确认 Render 仍追踪这个仓库的 `main`，且自动发布已开启。检查 Render 检测到归档提交并成功发布，打开新文章检查正文、图片和排版。

当前工作流只负责整理和 Git 提交，不调用 Render API，也不配置 GitHub Pages、Cloudflare 或域名。

## 整理规则

- 使用 HTML 解析器读取文件，整理时不执行存档内的 JavaScript。
- 读取微信原文链接、标题、`publish_time` 和 `js_content`。发布日期支持数字日期、中文年月日，以及 `Oct 31, 2026, 6:00 PM` 这样的英文日期。
- 保留原文件字节，包括正文、样式和内嵌图片。文件名取发布日期，不取下载时间，采用 `ColorsWorld_YYYY年M月D日 HH_标题.html`，月份和日期不补零。`HH` 为原文显示的发布小时（24 小时制），未显示时间时使用 `99`，真实午夜使用 `00`；不做时区转换。首页文字与最终文件名一致，但不含 `.html`。中文文件名禁用字符替换为 `_`，标题最多使用 160 个 UTF-8 字节。
- 旧文章不重命名、不改写，首页只插入新链接或缺少的年份列表。
- 同一天同标题视为重复，重复上传文件保留。历史标题存在清洗、截断等差异，因此不是对全部旧文章的绝对去重保证。
- 目标文件名冲突时拒绝覆盖，包括 Git 跟踪但未被首页索引的路径。
- 本文图片必须已内嵌为 `data:image/...`。已识别的正文音视频和嵌入媒体拒绝自动归档。检查并不保证所有 CSS 背景图、交互、第三方嵌入或不可见内容均已备份，成员仍应离线检查页面。
- 批次内独立处理文件。成功项可以提交；失败和重复项留在收件目录。失败项会使运行最终显示失败，摘要列出逐篇结果。

## 重试与并发

在 Actions 中打开对应运行，选择 **Re-run all jobs**；也可通过 **Run workflow** 处理当前所有待处理文件。

工作流串行运行，每次从最新 `main` 检出。若整理期间另有成员提交，推送可能因远端更新而失败。它不会强制推送；远端上传原件仍在，重新运行即可基于最新版本整理。不要因工作区产生了本地提交，就宣称已成功推送。

由 `GITHUB_TOKEN` 创建的提交不会递归触发同类 Actions，但 Render 由已有的仓库集成检测提交。本流程没有配置依赖机器人提交自动触发的第二个 GitHub 工作流。

## 本地维护与验证

需要 Node.js 22 或更新版本。在仓库目录中运行：

```sh
npm ci --ignore-scripts
npm test
npm run archive
```

`npm run archive` 会移动 `incoming/` 中的 HTML 并修改首页，运行前先查看 Git 状态。也可以在准备好 `index.html` 与 `incoming/` 的临时目录试运行：

```sh
node scripts/archive.mjs .tmp/example
```

临时目录应在项目内。不要将私人下载路径、登录信息、测试文章或临时文件提交到仓库。

CI 使用稀疏检出，不下载历史文章正文；Git 索引仍含旧路径，提交新文章使用 `git add --sparse`。这样无需每次整理都下载整个历史存档。除页面解析器 `parse5` 外，没有运行时服务或数据库。

本地 agent 归档的最终提交也可以直接放入 `articles/年份/` 并修改 `index.html`，不依赖 GitHub Actions 再运行。检查权限与分支规则，普通推送即可，不强制推送。

## 大文件

GitHub 网页上传单个文件上限为 25 MiB。超过此值、但仍在普通 Git 限制内的文件，可让 agent 或 GitHub Desktop 提交至收件目录；超过 GitHub 普通 Git 文件大小限制时，需要维护者另行设计存储方式。不要直接引入 LFS 并假设静态托管会把指针文件替换为文章内容。仓库已有的历史 LFS 配置不在本次改动中迁移。

## 以后迁移托管

保留 `index.html`、`articles/年份/` 和既有文章 URL，就不需要为了迁移而重写文章。实际迁移前需要核对平台的总大小、单文件大小、Git LFS、文件数量和构建限制，再验证中文路径、旧链接、HTTPS 和自定义域名。仓库含较大的历史存档，不应仅凭“支持静态 HTML”就承诺某个平台可以直接承载。

只有新平台验证通过后，再切换域名和现有发布方式；当前 Render 发布不受迁移计划影响。
